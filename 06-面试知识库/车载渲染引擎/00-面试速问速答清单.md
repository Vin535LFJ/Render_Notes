## A. OpenGL 渲染管线（最高频）

**A1 讲一下 OpenGL 渲染管线。**
四层作答：①数据流 硬盘→内存→显存→帧缓冲→屏幕；②职责 CPU 决定"画什么/怎么画"，GPU 决定"每像素什么颜色"；③阶段 顶点输入→顶点着色→图元装配→裁剪→透视除法→视口变换→光栅化→片元着色→逐片元测试与混合→写帧缓冲；④瓶颈映射 每阶段对应一类优化。
→ 收束句："可编程只有顶点和片元两级，所以工程上只能做三件事：少提交、少算、少搬。"

**A2 哪些阶段可编程？几何/细分着色器能不能用？**
顶点 + 片元。**OpenGL ES 标准管线不含几何着色器与细分着色器**，桌面 GL 才有；ES 上个别 `EXT_*` 扩展提供，可移植性差 ⚠️。所以移动端/车机代码应假定这两级不存在。

**A3 OpenGL 状态机模型的代价在哪？**
全局可变状态 + 命令流；每次 draw 驱动要做状态校验、资源就绪检查、shader 与绑定一致性验证 ⚠️；改状态（换纹理/换 program）会让 GPU 流水线"换装"。→ 这正是 Vulkan/WebGPU 用 PSO 把状态一次性固化的动机。

**A4 哪些调用会把异步的 GL 变成同步点？**（做性能必答）
`glReadPixels`、`glGetError`、各类 `glGet*`、`glMapBuffer` 全量映射、覆写正在使用的 VBO、`glFinish`、每帧 `glTexImage2D` 重分配。
→ 加分："移动端我先找同步点，再怀疑 DrawCall 数量——一次回读的气泡顶得上几百次 draw。"

**A5 GL 命令是异步的，我怎么知道 GPU 真的画完了？**
`glFenceSync` + `glGetSynciv`/`glClientWaitSync`，或 EGL sync（`eglCreateSyncKHR` + `eglClientWaitSyncKHR`）。不要用 `glFinish` 把整条管线排空。✅

**A6 VBO / EBO / VAO 各自职责？**
VBO 存属性数据，EBO 存索引（实现顶点复用），VAO 记录"属性指针 + EBO 绑定 + 启用状态"。切换网格只需 `glBindVertexArray`，是最便宜的状态切换。ES2 靠 `OES_vertex_array_object`，ES3 起核心 ✅。

**A7 透视除法发生在哪一步？NDC 范围是多少？**
裁剪后对 `gl_Position` 做 `(x,y,z)/w` 进入 NDC。GL 的 NDC 是 `[-1,1]³`；Vulkan/Metal/WebGPU 的 z 是 `[0,1]`，且 Y 轴向下 ✅ → 跨 API 移植必须处理 Z 范围与 Y 翻转两个差异。

**A8 光栅化怎么决定像素归谁？相邻三角形为什么不会重不漏？**
用三角形边方程（half-space）做覆盖判定，配合 **top-left fill rule** 这类统一约定 ⚠️（跨 API/驱动一致性建议实测）。

**A9 为什么透视校正插值不可省？**
屏幕空间线性插值只对"仿射量"成立；UV 在透视下不是线性量，不校正会出现纹理拉伸/网格扭曲。GPU 用 `1/w` 加权插值 ✅。

**A10 背面剔除在哪个阶段？为什么它对性能重要？**
图元装配阶段（光栅化之前）✅。剔除让被遮挡背面根本不产生片元，比在 shader 里 discard 便宜几个数量级——因为它省的是填充率与带宽。

**A11 `glScissor` 和 shader 里 discard 怎么选？**
能用 scissor（矩形区域限定）就用它：固定功能阶段就不产生片元，零混合成本；discard 只在异形遮罩且透明像素占比高时用，且可能关闭 Early-Z ⚠️。

**A12 `glClear` 有成本吗？怎么省？**
有，等于一次全屏写入。不需要保留的附件用 `glInvalidateFramebuffer`（ES3 核心）/`glDiscardFramebufferEXT`（ES2 扩展）告诉驱动"别 load 也别 store" ✅。Vulkan/Metal 里对应 load action=DontCare。

**A13 VSync、双缓冲、三缓冲分别解决什么？**
双缓冲+VSync 解决撕裂；三缓冲解决"CPU/GPU 超时导致的帧节奏抖动（pacing）"，代价是多一帧排队延迟与一屏显存 `[经验值]`。
→ 关键区分：**长帧（jank）** 和 **节奏抖动** 是两个不同问题，三缓冲治不了前者。

**A14 `eglSwapBuffers` 之后 back buffer 内容还在吗？**
不保证。查 `eglQuerySurface(EGL_SWAP_BEHAVIOR)`，默认多为 `EGL_BUFFER_DESTROYED`；设成 `PRESERVED` 会引入一次额外拷贝，移动端功耗代价明显 ⚠️。

## B. 帧缓存与离屏渲染（面试官最爱深挖）

**B1 FBO 是什么？三种"可画的目标"分别是什么？**
FBO 是**附件容器**（不是显存本身）。目标有三类：默认帧缓冲（窗口 back buffer，唯一能直接上屏、受 swap 控制）、FBO（离屏，产物是纹理/renderbuffer）、Pbuffer（老式 EGL 离屏，ES 上基本被 FBO 取代）⚠️。

**B2 attachment 绑 texture 和绑 renderbuffer 的区别？**
纹理：可再采样（RTT/后处理必须用它）。Renderbuffer：纯可写存储、**不可直接采样**，用于深度/模板、MSAA 目标、无格式要求的高性能写入 ✅。

**B3 帧缓冲"完整"的条件？怎么检查？**
至少一个附件、附件参数合法且非空、各附件尺寸/层/采样数一致（否则 `FRAMEBUFFER_INCOMPLETE_DIMENSIONS`/`_MULTISAMPLE`）、internalformat 组合被支持（否则 `GL_FRAMEBUFFER_UNSUPPORTED`）。每次创建和**分辨率变更后**都调 `glCheckFramebufferStatus` ✅。
→ 车机答法："检查失败不是报错，是要立刻降级到不做特效的直出路径，显示安全优先于画质。"

**B4 阴影的深度图能当纹理采样吗？**
可以。把 `GL_DEPTH_COMPONENT16/24` 或 `DEPTH24_STENCIL8` 作为纹理附件，主 pass 用 `sampler2D` 采样比较——这就是 Shadow Map 的基础 ✅。

**B5 为什么必须 Ping-Pong 两个 FBO？**
同一纹理同时作为渲染目标和采样源是反馈循环，结果未定义/黑屏 ✅。`GL_EXT_shader_framebuffer_fetch` 等扩展提供合法读当前片元的路径，但按 SoC 判定 ⚠️❗。

**B6 `glBlitFramebuffer` 的规则和坑？**
源/目标不能同一个 FBO；深度/模板 blit 不允许缩放且两侧格式必须相同；color blit 缩放时 `GL_LINEAR` 支持不一，多数用 `NEAREST` ⚠️；MSAA resolve 的标准路径就是 blit ✅。它是显存内 D2D，不经 CPU 但**仍消耗外部带宽**。

**B7 MSAA 原理、为什么比 SSAA 便宜、解决不了什么？**
每像素多个**覆盖采样点**，但片元着色器只跑一次 ✅；SSAA 是整体超采样，着色次数随采样数平方增长。MSAA 只能治**几何边缘锯齿**，对 shader 内部高频（高光闪烁、细节贴图）无效 → 需 FXAA/TAA。

**B8 离屏渲染比直接画屏幕上贵在哪？**
①每个 Pass 一次 store + 下次一次 load 的外部带宽；②失去硬件 overlay 合成路径；③可能引入格式转换。→ 量化答法用 B21 的带宽账。

**B9 视频特效链里 FBO 起什么作用？**
把 `GL_TEXTURE_EXTERNAL_OES`（不能跨纹理采样、不能直接回读、内部仍是 YUV 语义）转成标准 `GL_TEXTURE_2D` RGBA，才能进多 Pass 特效链。详见 [02-解码与播放链路 §7](../../02-解码与播放链路/解码与播放链路.md)。

**B10 怎么把 GPU 像素交给 CPU 而不卡管线？**
PBO 异步回读 + fence + 双 PBO 轮转（代码见 01 号文档 §6.4）。
→ 更强的答法是反问："为什么需要回读？车机上更应把 `AHardwareBuffer`/EGLImage/dmabuf 直接交给下游（编码/AI/显示），回读本身当性能 bug。"

**B11 FBO 在某设备上黑屏，排障顺序？**
`glCheckFramebufferStatus` → 打印格式与尺寸 → 查 `GL_MAX_*` 与该设备格式支持表 → 逐项降级（去深度 / 换 RGBA8 / 降尺寸）→ 检查线程与上下文归属（跨线程创建纹理是常见原因）→ 检查是否读写同一纹理 → 检查 viewport。

**B12 一帧带宽账怎么算？**
`外部带宽 ≈ Σ(每 Pass 的 load+store 字节) + 纹理采样读 + 顶点读 + MSAA resolve`。
示例：1920×720 RGBA8 一次全屏 store ≈ 5.5 MB `[经验值]`，5 个全屏 Pass 含 load+store 即数十 MB/帧，60fps 就是 GB/s 量级 → **带宽比算力更早触顶** ⚠️。

**B13 多 Pass 的降本顺序？**
①合并 Pass（Kernel Fusion，可结合的滤镜合成 1 个 shader）②降分辨率（模糊/Bloom 用 1/2、1/4）③省附件（invalidate 不需要的深度）④换格式/压缩纹理 ⑤最后才谈加算力。

## C. DrawCall 与提交优化（岗位核心）

**C1 DrawCall 的成本由哪几部分组成？**
CPU 侧：驱动命令打包与状态校验、用户态→内核态提交、命令流写入；GPU 侧：绑定切换（VBO/纹理/program）带来的流水线换装、顶点抓取启动成本。详见 [图形与GPU工程 §3](../../03-图形与GPU工程/图形与GPU工程.md)。

**C2 "DrawCall 多累的是 CPU"为什么？**
GPU 执行本身并行高效；每次 draw 前的状态验证、坐标/包围体计算、命令打包都由 CPU 串行完成。类比："项目经理喊话喊到嗓子哑，装修工其实不累。" ✅

**C3 DrawCall 从 1000 降到 10，帧率没变——解释并给下一步。**
说明瓶颈不在提交端，而在 GPU 填充率/带宽/Overdraw 或片元着色饱和。下一步：①降分辨率实验（帧率明显变→片元侧）；②看 profiler 时间轴是否有 GPU 空闲气泡（有→CPU 提交）；③查 Overdraw 与半透明层数。见 [面试知识库 Q7](../面试知识库.md)、[图形与GPU工程 §3.3](../../03-图形与GPU工程/图形与GPU工程.md)。

**C4 合图、合批、压缩纹理分别治什么病？**
合图治**状态切换**（少 `glBindTexture`）；合批治**CPU 提交频次**（少 draw）；压缩纹理治**显存容量与带宽**。✅ 三者不可互相替代。

**C5 GPU Instancing 的原理与在 GLES 上怎么传 per-instance 数据？**
一次 draw 提交 N 份相同几何，靠 `glVertexAttribDivisor`（ES3.0 核心 ✅）让某些属性每 N 个实例才前进一次。per-instance 数据通道：①实例属性 + divisor；②UBO 数组 + `gl_InstanceID`/`gl_InstanceID` 索引 ⚠️（ES3 里 instance ID 需 `EXT_draw_instanced`/ES3.0 的 `gl_InstanceID`）；③SSBO（ES3.1+）。限制：UBO 尺寸与实例数上限、单批需同材质同网格。

**C6 材质与物体排序为什么能提速？**
按 program → 纹理 → 混合状态 排序，把同状态物体聚成一批；不透明按**前到后**让 Early-Z 生效，半透明按**后到前**保证混合正确 ✅。

**C7 间接绘制 / GPU-driven 渲染能做到什么程度？**
ES3.1 起有 `glDrawArraysIndirect`/`glDrawElementsIndirect` ✅，可用 compute shader 做 GPU 剔除写回参数缓冲，CPU 不再逐个提交 ⚠️（移动端驱动实现质量与收益差异大，需实测）。桌面/Vulkan 侧更成熟：mesh shader、meshlet、GPU culling + indirect。

**C8 除了 DrawCall 数量，还有哪些提交侧优化？**
减少绑定切换（VAO 复用、图集）、UBO 按帧共享、命令流批处理（一次提交多 draw）、避免同步点、多线程录制（Vulkan 天然友好，GL 需共享上下文 + 多 command queue ⚠️）、把剔除与排序放 Job/compute。

**C9 顶点缓存与索引顺序相关的问题？**
`GL_UNSIGNED_SHORT` 索引上限 65535，超了用 `GL_UNSIGNED_INT` ✅；索引顺序影响 GPU 后变换顶点缓存命中率 → 用 meshoptimizer 的 vertex-cache/overdraw 优化重排（见 F 组）。

**C10 剔除体系有哪几层？**
①视锥剔除（CPU，包围体测试）②背面剔除（GPU 固定）③遮挡剔除（HZB/occlusion query，代价是要回读→易引入同步 ⚠️）④层级/分区剔除（PVS、空间划分）⑤LOD 与 HLOD 减少几何量。

## D. Shader 与手写题

**D1 GLSL ES 的精度限定符陷阱？**
`lowp/mediump/highp`；顶点着色器里位置/UV 用 `mediump` 在大场景或高分辨率图集上会抖动/条带 ⚠️。实践：与位置、UV、深度相关一律 highp；颜色、方向、归一化量用 mediump。片元默认精度必须显式声明 `precision` ✅。

**D2 attribute/varying/uniform 与 in/out 的关系？**
ES1/ES2 语法 vs ES3(GLSL ES 3.00) 的 `in/out`；`varying` 插值开销与**插值器数量**直接相关，能进 uniform/常量就别占 varying ✅。追问： varying 用满会链接失败或降级。

**D3 `dFdx/dFdy/fwidth` 用来干什么？**
屏幕空间导数：自动 mip 选择、法线扰动（bump/parallax）、边缘检测、后处理重建法线。ES2 需 `OES_standard_derivatives`，ES3 内置 ✅。

**D4 采样相关的必考点？**
纹理必须完整定义（min filter 与所有 mip level 都存在，否则采样结果未定义/黑 ✅）、半像素偏移 `(v+0.5)/size`、`textureLod` 手动指定层级、`TEXTURE_MAX_ANISOTROPY` 需 `EXT_texture_filter_anisotropic` ⚠️。

**D5 分支的性能问题怎么说？**
`if (uniform 条件)` 基本无害（整批一致）；`if (varying 条件)` 在 SIMD 里两侧都可能执行 → 尽量用 `mix/step/clamp` 无分支重写，或把分支上移到 CPU/Pass 层 ✅。

**D6 Shader 编译卡顿怎么解决？**
①启动阶段预热（`glFinish`-free 的方式：创建/链接后立即做一次空 draw）；②program binary 缓存（`GL_EXT_program_binary`/`GL_EXT_replay_paths`，按驱动版本失效 ⚠️）；③减少变体数量与预处理宏；④Vulkan/WebGPU 可用离线 SPIR-V/编译期固化。

**D7 必须能手写的 12 个 shader（面试官会当场让写）**
1) YUV(I420/NV12)→RGB（BT.601/709、limited/full range）
2) 可分离高斯模糊（两次 pass + 降分辨率）
3) Bloom（bright pass → 模糊 → 合成）
4) 亮度/对比度/饱和度/色温 调整
5) 3D LUT 调色（`sampler3D` + 半像素偏移）
6) 图集/合图 UV 采样（含 rect 缩放与翻转修正）
7) 径向模糊 / 暗角 / 镜头失真
8) 顶点动画：旗帜飘动、水波、呼吸缩放
9) 菲涅尔边缘光（rim light）
10) 溶解（dissolve）：噪声图 + alpha 阈值 + 边缘高光
11) 描边（背面外扩法 vs 边缘检测法）
12) 半透明叠加与预乘 alpha 输出（含黑边消除）
→ 现成代码与逐行解释见 [05-Shader编程与手写题库](./05-Shader编程与手写题库.md)；YUV/Alpha 部分已有 [图形与GPU工程 §2](../../03-图形与GPU工程/图形与GPU工程.md)。

**D8 手写 YUV→RGB 会被追问什么？**
矩阵来源（BT.601/709/2020 与 VUI 元数据）、range（limited 16-235 vs full 0-255）、色度上采样方式、为什么用三条纹理而不是 `glReadPixels`、以及 stride/padding（见 [音视频基础理论 §2.2](../../01-基础理论/音视频基础理论.md)）。

**D9 GLSL / HLSL / Cg / MSL / WGSL 怎么迁移？**
GLSL→HLSL：`vec/floatN` 对应、`mul(v,M)`→`mul(M,v)` 与行/列主序、函数名差异（`mix/lerp`、`fract/frac`、`inversesqrt/rsqrt`）、语义标注（`SV_POSITION`/`TEXCOORD`）、`discard` 一致；MSL 偏 HLSL 风格 + `thread` 概念；WGSL 强类型 + `@group/@binding` 显式绑定。Unity 用 HLSL(经 HLSLcg) 转各平台；Cocos 用 GLSL(自有 shader 编译链) → 见 E 组与 Cocos/Unity 文档。

## E. 3D 图形学原理

**E1 讲一遍坐标空间链路。**
Local(Model) → World → View(Eye) → Clip(齐次) → NDC → Screen。MVP 复合：`gl_Position = P·V·M·vec4(pos,1)` ✅，注意 GLSL 列主序下矩阵从右往左作用于列向量。

**E2 透视投影矩阵关键点？**
`fov / aspect / near / far`；产生 `w = -z` 供透视除法；**深度被压缩到非线性**，精度集中在 near 附近 → near 别设太小，far 别无脑大 ✅。UI/2D/正交场景用正交投影（无透视变形、深度线性）。

**E3 为什么会有 z-fighting，怎么治？**
深度精度不足导致两个近邻面在 Z 缓冲里翻转。治法：拉大 near、缩短 far、分层场景用不同 near/far、`glPolygonOffset`、32 位浮点深度 `GL_DEPTH_COMPONENT32F`（ES3 ✅）、几何真正分离。

**E4 法线为什么需要"逆转置矩阵"变换？**
非均匀缩放会让面法线不再垂直；正确变换是 `(M⁻¹)ᵀ` ✅。追问：正交/均匀缩放时可直接用 M 的旋转部分。

**E5 欧拉角 vs 四元数？**
欧拉角有万向锁与插值不平滑问题；四元数用 `slerp/nlerp` 平滑插值、存储紧凑，但需归一化防漂移 ✅。

**E6 Lambert / Phong / Blinn-Phong 差别？**
漫反射余弦律 → 镜面用反射向量与视线夹角 → Blinn 用半程向量 `H` 替代反射向量省一次点积/幂运算（半角模型，高光形状略有差异）✅。追问：为什么不物理正确（不满足能量守恒、高光随光强越界）。

**E7 PBR 讲清楚三件事。**
①**微表面**：粗糙度→GGX/Tinmann 法线分布（NDF）；②**能量守恒**：反射不能多于入射，金属度决定高光/漫反射分配；③**Fresnel**：掠射角反射增强（Schlick 近似）。Cook-Torrance：`D·F·G / (4·N·L·N·V)`，配合 IBL（辐照度图 + 预过滤环境图 + BRDF LUT）✅。
→ 车机追问"移动设备上 PBR 成本"：答"解析光源用简化 GGX 或 IBL only、避免逐像素 sqrt/幂运算、用 half precision、必要时用 baked lighting + 少量动态光"。

**E8 阴影方案怎么选？**
Shadow Map（深度图 + PCF 软化 + bias 治 acne/peter-panning）→ CSM 分级解决大范围 → VSM/ESSM 获得廉价软阴影但 light bleeding。实时点光源立方体阴影在移动上很贵；座舱里多数是"固定太阳角 + 烘焙 + 少量 SSAO" `[经验值]`。

**E9 前向 / 延迟 / Forward+ 怎么选？**
| 维度 | 前向 | 延迟 | Forward+ |
|---|---|---|---|
| 光源数 | 少（成本×光照数） | 多（一次 g-buffer） | 多（tile 化分簇） |
| 材质 | 自由 | 受 g-buffer 精度限制 | 自由 |
| MSAA | 易 | 难（几何 pass 可，光照 pass 无效） | 较易 |
| 带宽 | 低 | 高（写多个目标） | 中 |
| 半透明 | 天然 | 需额外处理 | 天然 |
车机（TBDR + 带宽紧张 + UI 叠加多）多数走**前向/Forward+ 定制** ⚠️。

**E10 后处理链的正确顺序？**
HDR 场景渲染 →（SSAO）→ 光照/反射 → 透明合成 → **Tone Mapping** →（色彩分级/LUT）→  gamma/sRGB 编码 → 上采样/UI 叠加。Tone map 与大部分滤镜必须在**线性空间**做，UI/文本一般在最后按显示域叠加 ✅。

**E11 抗锯齿体系全景？**
SSAA（超采样，画质最好成本最高）/ MSAA（几何边缘，着色一次）/ FXAA·SMAA（后处理便宜，糊细节）/ TAA（时域累积，最省且治闪烁，但有 ghosting，需 motion vector）/ 与 alpha-to-coverage。移动端常用 MSAA(2/4x) 或 FXAA 折中 ⚠️。

**E12 色彩管理必问：为什么要线性工作流？**
人眼对暗部更敏感，sRGB 用幂律编码把码字分配到人敏感区。GPU 采样得到的是**编码后的非线性值**，直接做混合/缩放/光照会在暗部偏色与出现暗边 → 严格做：先解码到线性，算完再编码回显示域 ✅。
→ 追问"那视频为什么不做线性化"：视频素材本身已是显示域编码，直接按 sRGB 上屏是约定做法；做特效/合成时才需线性。⚠️有条件成立

**E13 HDR 通路？**
元数据三件套：`colour_primaries` / `transfer_characteristics` / `matrix_coeffs`（H.264/HEVC VUI，MP4 `colr` box）✅；HDR TF 用 PQ（绝对亮度）或 HLG（相对，广播兼容）；到 SDR 屏需 tone mapping（Reinhard/Hable/ACES/BT.2390）+ 色域压缩。

**E14 Mipmap 与过滤体系？**
min 滤镜 6 种（nearest/linear × mip nearest/linear，即最邻近、双线性、三线性的层级选择）+ 各向异性 `EXT_texture_filter_anisotropic`；mipmap 显存约 +1/3 ✅；生成 `glGenerateMipmap`；`baseLevel/maxLevel/minLod/maxLod` 可调。追问：为什么 mipmap 同时是**画质**和**带宽**优化（缩小采样邻域、cache 局部性）。

**E15 移动端 GPU 架构为什么是必答？**
TBDR（Mali/PowerVR/Adreno/Apple 一类）把屏幕切成 tile，像素在**片上 tile memory** 里渲染完再 resolve 到外部显存；IMR（桌面）直接对外存帧缓冲读写。推论 ✅：
① Overdraw 在 tile 内便宜、但 store/load 与深度写回仍走外部带宽；
② 每个额外 FBO Pass = 一次 store + 一次 load（这是多 Pass 特效链在移动上贵的根因，也解释了 Kernel Fusion 收益来源）；
③ MSAA 相对便宜（tile 内多采样）；
④ 需要显式 load/store 语义（Vulkan subpass、Metal loadAction/storeAction）来避免无谓 load。

## F. 3D 几何原理

**F1 一个网格的运行时数据构成？**
位置、法线、UV（可多套）、切线/副切线、顶点色、权重与索引（蒙皮）、以及可选的骨骼索引压缩；加索引缓冲、包围体、LOD 层级、材质分区（submesh）。

**F2 法线怎么算？硬边怎么办？**
面法线 = 相邻边叉积；顶点法线 = 邻面加权平均。要硬边/UV 接缝就必须**复制顶点**（顶点属性不同则无法共享）→ 这是模型顶点数放大的主因 ✅。

**F3 切线空间与法线贴图？**
用 UV 方向构造 TBN 矩阵，把法线从贴图空间变换到世界空间；需与烘焙工具用同一约定（业界事实标准是 MikkTSpace），否则出现接缝/朝向错误 ⚠️。副切线可重建（`derivatives`），省数据但花算力。

**F4 UV 展开的坑？**
接缝处采样跨到另一侧（需留边距/padding）、拉伸导致纹素密度不均、跨 atlas 子图渗色（双线性/mipmap 在边界跨图采样 → padding/bleed 或 clamp + 内缩 UV）✅。

**F5 蒙皮与骨骼？**
每顶点 4 个影响（可 8）；运行时用 bone matrix palette（UBO/纹理）做 GPU 蒙皮；UBO 大小限制→超出需分块或纹理存矩阵；`gl_InstanceID` + 实例化可批量画同骨架不同姿态 ⚠️。追问：为什么要烘焙顶点动画（AnimTexture）——省蒙皮算力与保证可合批。

**F6 网格压缩与优化？**
离线：Draco（几何压缩，需解码）、meshoptimizer（顶点缓存优化 + 过绘制优化 + 索引/属性量化）、纹理/顶点格式压缩（位置 16bit 归一化、UV 归一化）。运行时：LOD 链、HLOD 合并、billboard、遮挡与视锥剔除。

**F7 包围体与相交测试？**
球/AABB/OBB/k-DOP；与视锥 6 面做分离轴测试（经典 6 平面球测试最快）。层次加速：BVH/kd-tree/八叉树；射线求交用于拾取、点云/激光雷达可视化。

**F8 曲面与程序化几何了解到什么程度？**
Bezier / Catmull-Rom（轨迹插值常用）、B-spline/NURBS（CAD 与车身分块曲面）、细分曲面（Catmull-Clark/Loop）；实时里更常见的是 SDF（圆角/遮罩/字体/AA 形状，一行 shader 出抗锯齿形状）与程序化网格生成（HUD、道路带、粒子 ribbon）✅。

**F9 模型格式怎么选？**
OBJ（静态、无动画、文本）、FBX（DCC 交换、二进制、专有）、**glTF**（运行时友好、直接映射 GPU buffer、PBR 标准、扩展机制）✅。车机/HMI 建议 glTF/GLB + Draco/Meshopt 压缩 + KTX2/BasisU 纹理。

## G. Vulkan 与显式 API

**G1 Vulkan 与 OpenGL 的心智模型差异？**
GL：全局可变状态机 + 驱动猜你要干什么；Vulkan：显式对象图 + 显式内存 + 显式同步 + 预编译 PSO，驱动把工作前移到创建期，运行期近乎零校验 ✅。

**G2 报一下核心对象。**
`VkInstance / VkPhysicalDevice / VkDevice / VkQueue / VkCommandPool / VkCommandBuffer / VkRenderPass / VkPipelineLayout / VkDescriptorSetLayout / VkDescriptorPool / VkPipeline(PSO) / VkBuffer+VkDeviceMemory / VkImage / VkImageView / VkFramebuffer / VkSwapchain / VkSemaphore / VkFence / VkSampler / VkDeviceSize 对齐`。

**G3 Fence 和 Semaphore 的区别？**
Semaphore = **GPU↔GPU** 顺序（跨队列/跨阶段，不阻塞 CPU）；Fence = **GPU→CPU** 通知（帧循环里等前面几帧）。两者不可互换 ✅。

**G4 屏障（Barrier）有哪几类、要表达什么？**
`VkImageMemoryBarrier`（布局/队列族所有权的可见性）、`VkMemoryBarrier`（全局内存）、`VkBufferMemoryBarrier`（buffer）。每条要写 **source stage + source access mask → dst stage + dst access mask**（+ 所有权转移）。写错就是数据竞争或无谓气泡 ✅。

**G5 RenderPass/Subpass 为什么对移动 GPU 重要？**
它们把"这一段渲染的附件从哪 load、最后怎么 store、中间是否留在 tile memory"显式化。subpass + input attachment 让相邻全屏 Pass 留在 tile 内、**不走外部带宽**，并自动推导依赖 ✅。
→ 与 B13/B15 串起来就是车机多 Pass 特效链的正确答案。

**G6 PSO 为什么快、代价是什么？**
创建期完成驱动优化与代码生成，运行期切换无校验；代价是**变体爆炸**（状态组合数）与创建耗时 → 需要异步创建、PSO cache、预热（车机冷启动会因此踩坑 ⚠️）。

**G7 内存与 tiling 必答点？**
`vkGetBufferMemoryRequirements` → 按 memory property 选（DEVICE_LOCAL/HOST_VISIBLE_COHERENT…）→ 大块分配 + 子分配（VMA）；`linear` vs `optimal` tiling 决定能否直接采样与 copy 方式；buffer→image 拷贝要处理行对齐 `bufferRowLength` 与子资源 ✅。

**G8 Swapchain 与呈现模式？**
`FIFO`（等 vsync，永不撕裂，延迟稳定）/ `IMMEDIATE`（可撕裂最低延迟）/ `MAILBOX`（不撕裂且不等 vsync，需 3+ 图像）/ `FIFO_RELAXED`。车机仪表多选 FIFO `[经验值]`；跨 API 的显示同步用 `VkPresentTimeGOOGLE`/`VK_EXT_present_timing` ⚠️。

**G9 什么时候 Vulkan，什么时候 GLES？**
Vulkan：多核提交、显式资源与内存、可预测帧时间、需要 compute/subpass 精细控制、桌面级画质。GLES：生态成熟、启动快、代码量小、认证与旧平台支持好。**车机现实**：不同 SoC/驱动成熟度差异大，多数项目要 GL/Vulkan **双后端**，抽象层设计比选哪个 API 更重要 ⚠️。

**G10 工程配套？**
Validation Layer（含 synchronized validation）、RenderDoc/Nsight/Arm Graphics Profiler、VMA、HLSL→SPIR-V(dxc)、`VK_KHR_external_memory_fd`/`VK_ANDROID_external_memory_android_hardware_buffer` 做零拷贝导入（见 [04-跨平台架构](../../04-跨平台与高性能架构/跨平台与高性能架构.md)）✅。

## H. Cocos（引擎题，按"分层+一帧调用链"答）

**H1 Cocos2d-x 的分层？**
应用层（Lua/JS/C++）→ 场景图（`Director`/`Scene`/`Node`/`Component`）→ 逻辑系统（`Scheduler`、`ActionManager`、`EventDispatcher`、`TextureCache`）→ 渲染层（`Renderer` + `RenderQueue` + `Command`）→ 设备抽象（v4 起的 gfx device：GLES/Metal/Vulkan 等 ❗版本细节待核实）→ 平台（`GLView`/窗口与 EGL）。

**H2 描述 Cocos 渲染一帧。**
`Director::mainLoop` → 更新逻辑（Scheduler/Action）→ `Scene::visit` 递归遍历节点 → 每个可绘制节点通过 **Assembler 生成 RenderCommand**（三角形类命令携带材质/纹理/顶点数据）→ 命令进入 `Renderer` 的队列 → `Renderer::render()` 按队列顺序提交到设备抽象 → 交换缓冲。
→ 关键理解：**节点不是"画"，而是"投递命令"**；遍历（CPU）与提交（渲染）解耦，才可能有排序与合批 ✅。

**H3 Cocos 的合批规则？为什么我的场景 DrawCall 高？**
能合批需：同一纹理/图集、同一渲染命令类型与材质、且**中间没有被不同 Z 序的物体打断**。破坏合批的常见原因：交替纹理、不同 Z、不同材质/混合状态、Label 用系统字体、`RenderTexture` 夹在中间、3D 与 2D 混排。
排查口径：①统计纹理切换次数与 program 切换次数；②看节点 Z 分布（global Z 排序会 2D/3D 交叉重排 ⚠️）；③图集是否碎片率高 ✅。

**H4 Cocos 的离屏/RTT 怎么做？**
`RenderTexture`（内部就是 FBO + 纹理，`begin/clear/end` 或 `beginWithClear`），常用于截屏、模糊背景、笔刷、动态 UI 合成、把复杂子树压成 1 个 DrawCall（代价：额外 Pass 与带宽，见 B13）✅。
追问：`preserveBacking` 的意义（不保留可省一次全屏 clear/copy ⚠️）。

**H5 Cocos Creator（3.x）与 Cocos2d-x 的关系与差异？**
Creator 是编辑器 + TypeScript 运行时路线，渲染层是 scene/pipeline 化：`RenderScene` + `Model/SubModel/Pass/Material` + `Batcher2D/Batcher3D` + forward/deferred pipeline + Web 端走 WebGL/WebGPU、原生端走 gfx-native ❗（类名与 pipeline 支持范围以官方文档为准）。Cocos2d-x 是 C++ 引擎本体路线。

**H6 引擎里的 shader 是怎么组织的？**
自有 shader 源 + 宏开关 + 变体（`technique/pass` 结构），编译到目标 GLSL 版本；材质实例 = 参数 + 变体选择。追问"如何做 shader 平台适配"→ 答：统一源 + 编译/预处理到 GLSL/HLSL/MSL/WGSL，加精度限定符与语义映射层 ✅。

**H7 Cocos 适合车机的理由与风险？**
理由：C++ 本体、体积小、启动快、源码可控、GLES/Vulkan 后端、2D/HMI 场景成熟、易嵌入系统级进程。风险：3D 高级特性（PBR/后处理/大场景管理）不如 Unity/UE 完整、生态与工具链需自补 ⚠️。
→ 若面试官问"你为什么适合改造它"：正好接 K 组（引擎内部定制）。

## I. Unity

**I1 Unity 渲染一帧的链路？**
PlayerLoop 驱动 → 场景图与 Animator/Job 更新 → 剔除（`CullResults`，按相机视锥 + LODGroup）→ 渲染队列分类（opaque/transparent/skybox 等，按距离与队列号排序）→ SRP 生成绘制命令 → GfxDevice 提交（Vulkan/Metal/GLES/DX）→ swap 与合成 ✅。

**I2 Built-in / SRP / URP / HDRP 的关系？**
Built-in 是 C++ 内置管线，可控性低；SRP（`ScriptableRenderPipeline`）把管线交给你用 C# 写；URP、HDRP 是 SRP 之上的官方管线实现。追问"为什么要用 SRP"→ 答：**为特定平台裁剪特性、自定义 Pass、控制带宽与内存、去掉不需要的开销** ✅（正是车机场景的动机）。

**I3 URP 里怎么加一条自定义渲染特性？**
`ScriptableRendererFeature` → 创建 `ScriptableRenderPass` → 指定注入点（如 `onBeforeRenderingOpaques`/`afterRenderingTransparents`）→ 在 `Execute` 里配 `CommandBuffer` + `DrawRenderers`/`Blit` → 通过材质/keyword 或 layer mask 控制生效范围 ✅。
→ 加分：说明它对应的底层就是"多一个 Pass + 一次 RT 切换"，要评估带宽（B12/B13）。

**I4 合批家族的区别（高频陷阱题）**
| 手段 | 减少 DrawCall? | 前提 | 备注 |
|---|---|---|---|
| Static Batching | ✅ | 静态、同材质 | 合并几何，增加内存 |
| Dynamic Batching | ✅ | 低顶点数、同材质 | 新版逐步弃用/被限制 ⚠️❗ |
| GPU Instancing | ✅ | 同网格同材质 | 每实例属性 |
| SRP Batcher | ❌ **不减 DrawCall** | shader 兼容（`UnityPerMaterial` CBUFFER） | 减少每 draw 的材质数据上传/设置成本 |
| BatchRendererGroup / Entities Graphics | ✅ | 数据驱动渲染 | 大规模实体，绕开传统 GameObject 路径 |
**"SRP Batcher 降不降 DrawCall" 是常被拿来筛人的问题**，标准答案：不降 DrawCall，降的是 CPU 提交侧的 material setup 成本 ⚠️（我按此写；已在核实中，待官方文档确认版本细节）。

**I5 Shader 变体为什么会出问题？**
`multi_compile` 全量进包（运行时可切）、`shader_feature` 只保留被材质用到的（可能被裁剪）；变体多导致包体、编译、首次使用卡顿；未预热的变体在运行时编译会造成帧尖峰 → `ShaderVariantCollection.WarmUp` ✅。车机冷启动要特别关注这一点。

**I6 Unity 的车机可行性？**
优势：3D 生态、编辑器效率、工具链成熟。风险：运行时体积与授权成本、冷启动时间、源码可控性（非开源）、功能安全认证路径、对多屏/系统合成的定制受限 ⚠️。Job/Burst/DOTS 提升 CPU 侧但不改变授权与可控性问题。

## J. 车载座舱专题（差异化加分区）

**J1 座舱显示链路的整体结构？**
SoC（GPU/DSP/VPU/DPU-显示子系统）→ Hypervisor（可选）→ OS（QNX / Linux / Android Automotive，常多系统并存）→ 合成器（QNX Screen / SurfaceFlinger / DRM-KMS）→ 显示接口（DP/eDP/MIPI-DSI/SerDes）→ 屏/ HUD。渲染引擎在 App/Service 层，**它的输出只是合成器的一层** ✅。

**J2 "谁来合成"为什么是关键架构题？**
硬件 overlay（DPU/合成器直接叠加，GPU 不参与混合）省电省带宽但变换能力弱；GPU 合成灵活但每帧付带宽与功耗。多屏（仪表+中控+副驾+HUD）同时要出图时，合成能力与显示管道分配就是瓶颈 ⚠️。

**J3 虚拟化下的 GPU 怎么共享？**
常见路径：virtio-GPU（客户机看到半虚拟 GPU，2D/资源共享）、venus/virgl 提供 VirGL 或 Vulkan 转发、设备直通（passthrough）+ 时间片仲裁、或 guest 走 CPU 渲染 + host 显示 ❗（具体名称与可用性需按平台文档核实）。核心矛盾：**算力与带宽隔离** vs **帧率与安全显示的确定性**。

**J4 功能安全怎么约束渲染？**
仪表/安全相关显示常落在 QNX/RTOS + 安全岛（R-CPU/MCU）路径；GPU/HMI 侧多为 QM 或低 ASIL，靠**独立的显示完整性监控**（黑屏/冻结/花屏检测、watchdog、E2E 校验的显示帧）兜底 ⚠️。渲染工程师的责任：确定性的帧时间、无阻塞主流程、异常时的安全降级画面。

**J5 车机渲染的时间类硬约束？**
冷启动到首帧（仪表出图）、倒车影像显示时间、开机动画与 3D 车模加载的抢占关系、长时运行的稳定性（数小时不泄漏不降频）。数值多为项目/法规相关约定，**面试请用"经验值 + 我们项目的实际口径"表达** `[经验值]`❗。

**J6 座舱特有的渲染工作负载？**
① 3D 车模与旋转交互（高帧率 + 材质写实）；② AVM 环视拼接与去畸变（视频 + GPU warp，常在显示子系统或专用模块，或 GPU compute ⚠️）；③ SR/ADAS 环境可视化（道路/车道线/目标框/点云）；④ 视频与流媒体（解码纹理零拷贝进渲染，见 [02](../../02-解码与播放链路/解码与播放链路.md)）；⑤ 大量 UI/字体/圆角/动效叠加（Overdraw 与图集管理是主战场）；⑥ HUD 与 AR-HUD 的对位与低延迟。

**J7 车机性能工程与手机有何不同？**
共享 DDR 的多主设备（GPU/VPU/DPU/Camera）带宽竞争、长时间高温与热预算、多屏多帧率、系统级合成带来的额外拷贝、可观测性差（不能随便装 profiler）、必须做**确定性**而不是峰值。→ 这些点讲出来，比背 API 更能证明你懂车载。

**J8 HMI 引擎生态了解？**
Kanzi、Qt/QML（含 AGL 生态）、Unity/UE、Cocos、Windriver 等；自研引擎通常为了**可控、启动时间、内存、与系统合成器直连、认证与长期维护** ✅。面试若问"为什么自研"，就从这 5 条答，别只说"能力不够"。

## K. 渲染管线定制与引擎内部改造（高级工程师的分水岭）

**K1 "如何给引擎加一条自定义渲染特性"的标准流程？**
需求→画质/带宽/延迟预算（先算 B12 的账）→ 选定注入位置（哪个 Pass、什么时机）→ shader（含精度与平台宏）→ RT/资源生命周期（复用池，别每帧重建）→ 特性开关与分级（低端设备关闭）→ 平台可用性探测与**回退路径**→ 指标接入（帧时间、带宽、DrawCall、Pass 数）→ A/B 实测（设备矩阵、样本量、置信区间）→ 文档化边界条件。
→ 用 [05-项目实战 §5](../../05-项目实战/项目实战指南.md) 的评测方法论讲这一段，说服力最强。

**K2 RHI/抽象层怎么设计才不烂？**
最小公共集 + 平台扩展通道（不追求"最大公约数"，允许能力查询与后端专有路径）；资源句柄与生命周期在抽象层统一，命令录制在后端展开；PSO/Program 编译与缓存策略下沉；显式暴露 load/store 语义与附件意图（否则移动后端无法省带宽）✅。

**K3 引擎内部的资源与显存管理必答点？**
大块分配 + 子分配、驻留（residency）与优先级、按场景/层的预算与淘汰、异步上传队列（避免主线程 `glBufferData`）、对象池与"帧内不分配"红线（呼应 [图形与GPU工程 §5.3](../../03-图形与GPU工程/图形与GPU工程.md)）、纹理压缩按平台分发包 ❗。

**K4 卡顿与掉帧的定位套路？**
①先分类：CPU 提交慢 / GPU 算不完 / 显示端背压 / 外部（内存回收、热降频、其它主设备抢带宽）；②时间轴工具看气泡（Frame Debugger、RenderDoc、平台 profiler）；③做"降分辨率实验"与"去特效实验"二分；④统计口径固定：帧时间分布 p50/p95/p99 + 掉帧率，而非平均 FPS ✅。

**K5 与系统/显示子系统的对接边界？**
渲染引擎负责出图；合成、色彩管理到面板、时序（vsync）、多屏分配通常属于系统层。定制工作常落在这里：EGL 平台/扩展选择、直出 overlay 层、脏矩形/局刷、零拷贝导入（dmabuf/AHardwareBuffer/EGLImage）✅ → 见 [04-跨平台架构](../../04-跨平台与高性能架构/跨平台与高性能架构.md)。

**K6 被问"你改过引擎的什么、为什么这样改"怎么答？**
三段式：①现象与量化基线（改前指标）；②定位到的机理（哪个阶段/哪种成本）；③改动方案 + 边界与未解决问题 + 回退开关。绝不只说"我加了个功能"。→ 现成素材可复用 [05-项目实战](../../05-项目实战/项目实战指南.md) 的 testKTX 重构故事，把它重述为"渲染管线定制 + 提交链路改造"。
