## 1. 两条主线的分界

| 维度 | 本地文件播放 | 网络流媒体 | 实时采集 |
|---|---|---|---|
| 数据源 | 文件 / 本地缓存 | manifest + 分片 | Camera sensor |
| 时序特征 | 可随意 seek、可预读 | 分片到达、码率可变 | 固定帧率、强实时 |
| 核心问题 | 解码、渲染、同步 | ABR、首帧、卡顿、DRM | 零拷贝、格式、延迟、曝光 |
| 典型失败 | 文件损坏、格式不支持 | 丢包、码率切换、CDN 超时 | 帧丢弃、权限、带宽不足 |
| 延迟目标 | 可接受 100–500 ms | VOD 秒级，直播 2–30 s | 预览 <100 ms，倒车 <2 s ❗ |

本地播放的"解封装 → 解码 → 渲染"三段式仍然成立；流媒体和采集只是在**解封装之前**和**渲染之前**各加了一段。

```
网络：DNS/TLS → manifest → init segment → media segments → demux → decode → render
采集：sensor → ISP → ImageReader/Surface → GPU 转换 → 合成/编码
```

## 2. 流媒体协议

### 2.1 HLS

Apple 提出，核心是 **m3u8 播放列表 + 分片**：

```
#EXTM3U
#EXT-X-VERSION:9
#EXT-X-TARGETDURATION:4
#EXT-X-MEDIA-SEQUENCE:120
#EXT-X-MAP:URI="init.mp4"
#EXTINF:4.0,
seg_120.m4s
#EXTINF:4.0,
seg_121.m4s
```

| 元素 | 作用 |
|---|---|
| Master playlist | 列出多档码率（variant streams） |
| Media playlist | 某一档码率的分片列表 |
| `EXT-X-MAP` | fMP4 的初始化段（moov） |
| `EXT-X-KEY` | 加密方式与密钥 URI |
| `EXT-X-DISCONTINUITY` | 广告/切台导致的时间轴不连续 |
| `EXT-X-ENDLIST` | VOD 结束标记；直播没有 |

- 分片通常是 MPEG-TS 或 fMP4；新项目优先 fMP4。
- 每个分片应从关键帧开始，ABR 才能在分片边界切换。
- 直播列表会滚动，客户端定期重新拉取。

### 2.2 DASH

ISO/IEC 23009，核心是 **MPD XML + 分片**：

```xml
<MPD type="dynamic" availabilityStartTime="...">
  <Period>
    <AdaptationSet mimeType="video/mp4">
      <Representation id="v720" bandwidth="2500000" width="1280" height="720">
        <SegmentTemplate media="seg_$Number$.m4s"
                         initialization="init.mp4"
                         duration="4" startNumber="120"/>
      </Representation>
    </AdaptationSet>
  </Period>
</MPD>
```

| 概念 | 含义 |
|---|---|
| Period | 时间轴分段（广告、节目切换） |
| AdaptationSet | 同一内容的多种编码/码率 |
| Representation | 某一档具体码率与分辨率 |
| SegmentTemplate | 用模板生成分片 URL，避免逐个列举 |

DASH 更"工程化"：多 Period、多语言、DRM（CENC）、码率描述都更结构化；HLS 更简单、Apple 生态覆盖好。

### 2.3 CMAF

ISO/IEC 23000-19，目标是把 HLS 与 DASH 的媒体格式统一：

- 统一使用 **fMP4** 分片。
- 统一 **CENC** 通用加密。
- 支持 **chunked segment**：一个分片可以边生成边传输。

**收益**：同一套分片同时服务 HLS 和 DASH，CDN 只存一份；低延迟方案（LL-HLS/LL-DASH）都建立在 CMAF chunk 之上。

### 2.4 LL-HLS / LL-DASH

| 方案 | 机制 | 典型延迟 |
|---|---|---|
| HLS | 完整分片 + 播放列表刷新 | 6–30 s ⚠️ |
| LL-HLS | 部分分片（`EXT-X-PART`）+ 预加载提示 + 阻塞式列表刷新 | 2–5 s ⚠️ |
| DASH | 完整分片 | 4–20 s ⚠️ |
| LL-DASH | CMAF chunked + `availabilityTimeOffset` | 2–5 s ⚠️ |
| WebRTC | RTP/UDP + jitter buffer | <1 s ⚠️ |

LL-HLS 的关键：

- 分片切成 0.2–1 s 的 **partial segment**。
- 客户端用 `_HLS_msn` / `_HLS_part` 请求"我已有到第几段，给我更新的"，服务器阻塞到有新数据再返回。
- `EXT-X-PRELOAD-HINT` 让客户端提前建立下一个请求，减少 RTT。

### 2.5 协议选型

| 场景 | 建议 |
|---|---|
| 点播、iOS/Android 双端 | HLS 或 DASH + CMAF 双封装 |
| 低延迟直播 | LL-HLS / LL-DASH；交互更强选 WebRTC |
| 车载弱网 | HLS/DASH + 较大缓冲 + 保守 ABR |
| 安防/超低延迟 | RTSP/WebRTC，而不是 HLS |
| DRM 内容 | DASH/HLS + Widevine/PlayReady/FairPlay |

## 3. ABR 自适应码率

### 3.1 为什么需要

网络带宽在移动场景下剧烈波动。固定高码率会卡顿，固定低码率会糊。ABR 根据吞吐与缓冲动态选择 Representation。

### 3.2 两类决策依据

| 类型 | 依据 | 优点 | 缺点 |
|---|---|---|---|
| 吞吐型（Throughput） | 最近分片的下载速度 | 实现简单、反应快 | 估计噪声大，易误判 |
| 缓冲型（Buffer-based / BOLA） | 当前缓冲区水位 | 稳定、少切换 | 启动阶段信息不足 |
| 混合型 | 吞吐 + 缓冲 + 码率阶梯 | 工程主流（dash.js/ExoPlayer） | 参数多 |

简化规则：

```
若 buffer < 低水位：立即降档
若 buffer > 高水位 且 吞吐 > 目标码率 × 1.2 持续 N 个分片：升档
否则：保持
```

- **滞回（hysteresis）**：升档比降档更保守，避免来回抖动。
- **分片长度**：短分片适应快但开销大；2–4 s 是 VOD 常见折中，低延迟用 0.5–1 s。
- **启动策略**：先从中低档起播，缓冲稳定后升档；或根据 manifest 的 `bandwidth` 与首包探测选初始档。

### 3.3 码率阶梯

| 档位 | 分辨率 | 典型码率（H.264） | 典型码率（H.265/AV1） |
|---|---|---|---|
| 240p | 426×240 | 0.3–0.5 Mbps | 0.2–0.35 Mbps |
| 360p | 640×360 | 0.6–1.0 Mbps | 0.4–0.7 Mbps |
| 480p | 854×480 | 1.0–1.8 Mbps | 0.7–1.2 Mbps |
| 720p | 1280×720 | 2.0–3.5 Mbps | 1.2–2.2 Mbps |
| 1080p | 1920×1080 | 4.0–8.0 Mbps | 2.5–5.0 Mbps |
| 4K | 3840×2160 | 15–30 Mbps | 8–18 Mbps |

> 数值是行业常见区间 `[经验值]` ⚠️，实际由内容复杂度、编码器、GOP、帧率决定，不能直接当验收标准。

### 3.4 切换的工程约束

- **必须切换到关键帧**：分片边界应对齐 GOP；否则解码器要等下一个 I 帧，出现黑屏/卡顿。
- **解码器重配**：分辨率/编码变化时，部分平台需要 flush 或重建解码器；同编码、同 profile 的档位切换更平滑。
- **音频独立**：音频通常单独 AdaptationSet，视频切档不影响音频。
- **DRM**：切档不能改变密钥/加密方式，否则需要重新授权。
- **缓冲区**：切档后旧档缓存仍可播放，避免立即丢弃。

### 3.5 QoE 指标

| 指标 | 含义 |
|---|---|
| 首帧时间（TTFF） | 从点击播放到第一帧上屏 |
| 卡顿比（Rebuffer Ratio） | 卡顿时长 / 总播放时长 |
| 平均码率 | 反映清晰度 |
| 切换次数 | 反映稳定性 |
| 起播失败率 | 反映 CDN/协议健壮性 |
| 直播延迟 | 播放位置与 live edge 的距离 |

ABR 优化不能只看平均码率：**高码率 + 频繁卡顿**通常比**略低码率 + 零卡顿**体验更差。

## 4. 首帧、缓冲与低延迟

### 4.1 首帧时间花在哪

```
DNS → TCP/TLS → manifest → init segment → 首个媒体分片
   → demux → 解码器创建 → 首帧解码 → 纹理上传 → 第一帧 vsync
```

| 阶段 | 典型优化 |
|---|---|
| DNS/TLS | HTTP/2/3、连接复用、预连接 |
| manifest | 预取、缓存、CDN 就近 |
| 分片 | 预加载首分片、Range 请求、并行音视频 |
| 解码器 | 预热解码器池、提前 `configure/start` |
| 渲染 | Surface 提前创建、避免首帧特效链 |
| 上屏 | 等第一个 vsync，避免首帧撕裂 |

**TTFF（Time To First Frame）** 与 **TTFD（Time To First Decoded frame）** 要分开测：前者包含渲染与合成，后者只到解码输出。

### 4.2 缓冲策略

| 场景 | 目标缓冲 | 说明 |
|---|---|---|
| VOD 移动端 | 10–30 s | 平衡卡顿与内存 |
| 直播 | 3–8 s | 兼顾延迟与抗抖动 |
| LL-HLS/LL-DASH | 1–3 s | 依赖 chunked + 阻塞刷新 |
| 车载弱网 | 10–30 s | 隧道/地库优先保连续性 |
| 倒车影像 | 不缓冲 | 实时优先，丢帧也不能延迟 ❗ |

- 缓冲不是越大越好：越大越抗抖动，但内存、切台时间、直播延迟都变差。
- **启动缓冲**与**稳态缓冲**可以不同：先快速起播，再逐步加厚。
- 缓冲水位要按**可播放时长**算，不是字节数；不同码率下字节数不可比。

### 4.3 卡顿归因

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 起播慢 | manifest/首片慢、解码器初始化慢、Surface 未就绪 | 分段打点 TTFF |
| 播放中周期性卡 | 吞吐不足、ABR 降档不及时 | 看吞吐曲线与 buffer 水位 |
| 单次长卡 | CDN 超时、分片 404、DRM 授权失败 | 看 HTTP 状态与重试日志 |
| 音频断续 | 音频缓冲不足、重采样/变速 | 看 AudioTrack underrun |
| 画面冻结但音频继续 | 视频解码器 stall、渲染线程阻塞 | 看解码输出与 vsync |
| 音画不同步 | 主时钟漂移、丢帧策略错误 | 看 A/V drift 曲线 |

### 4.4 低延迟的代价

- 低延迟意味着更小的缓冲，弱网下更容易卡顿。
- LL-HLS 的阻塞刷新会占用连接，CDN/边缘节点要支持。
- 低延迟直播通常需要**追赶策略**：延迟漂移超过阈值时，轻微加速播放（如 1.05×）或跳帧，而不是无限累积。

## 5. 10bit、HDR 与 AV1

### 5.1 位深与像素格式

| 格式 | 位深 | 排列 | 说明 |
|---|---|---|---|
| NV12 | 8bit | Y 平面 + UV 交错 | 最常见 4:2:0 |
| NV21 | 8bit | Y 平面 + VU 交错 | Android 相机常见 |
| P010 | 10bit | 16bit 容器存 10bit，低 6 位补零 | HDR 常见输出 |
| P016 | 16bit | 16bit 容器存 16bit | 更高精度，少见于消费端 |
| RGBA1010102 | 10bit | 每通道 10bit + 2bit alpha | GPU 渲染目标常用 |

10bit 的意义：

- **减少 banding**：暗部渐变可用码值更多。
- **HDR 动态范围**：PQ/HLG 需要更高位深承载亮度。
- **编码效率**：同质量下 10bit 有时比 8bit 更省码率（减少量化噪声）。

> 10bit 不是"颜色更多"这么简单：如果显示面板只有 8bit，最终仍要 dither 回 8bit；链路中任何一段掉到 8bit，前面的 10bit 就白费。

### 5.2 HDR 格式

| 格式 | 传输函数 | 元数据 | 特点 |
|---|---|---|---|
| HDR10 | PQ（SMPTE ST 2084） | 静态（MaxCLL/MaxFALL） | 最通用，10bit，BT.2020 |
| HLG | HLG | 无/少量 | 场景参考，向后兼容 SDR |
| HDR10+ | PQ | 动态（逐场景/逐帧） | 三星主导 |
| Dolby Vision | PQ | 动态 | 专有，需授权，Profile 复杂 |

- **PQ** 是绝对亮度映射，适合母版级 HDR；**HLG** 是相对亮度，兼容旧 SDR 显示。
- 静态元数据描述整条视频的最大/平均亮度；动态元数据逐镜头优化。
- 显示端能力要通过系统 API 查询，不能假设"支持 HDR"就支持所有格式。

### 5.3 Android 上的 HDR 链路

```
容器/码流元数据（VUI）
  → MediaExtractor/MediaFormat（KEY_COLOR_* / KEY_HDR_STATIC_INFO）
  → MediaCodec 解码（P010）
  → Surface/SurfaceTexture（Dataspace）
  → HWC/GPU tone mapping
  → 显示面板
```

| 环节 | 关键点 |
|---|---|
| 元数据 | `colour_primaries`、`transfer_characteristics`、`matrix_coeffs`、`full_range_flag` 必须正确传递 |
| 解码输出 | 10bit 常用 P010 输出（平台常量可能为 `COLOR_FormatYUVP010`，按 API 版本与设备查询）⚠️ |
| 纹理格式 | GLES 用 `GL_EXT_texture_norm16` 的 `GL_R16_EXT`/`GL_RG16_EXT`；或 Vulkan `R10X6_UNORM_PACK16` 等 |
| 显示 | `Display.getHdrCapabilities()` 查询 HDR10/HLG/DV/HDR10+ |
| Tone mapping | 显示不支持目标 HDR 时，在 GPU 或 HWC 做一次，**不要重复做** |
| 截图/录屏 | HDR 内容转 SDR 需要明确的 tone mapping，否则过曝/发灰 |

**常见错误**：

- 把 P010 当 NV12 上传，画面发绿/发灰。
- 只传 `KEY_COLOR_STANDARD` 不传 `KEY_COLOR_TRANSFER`，显示端按 SDR 处理。
- 在 shader 里手动 `pow(2.2)`，同时纹理又是 sRGB 格式，二次解码。
- HDR 内容经过普通 8bit FBO 后丢失高光，再 tone mapping 已经晚了。

色彩与 tone mapping 的数学见 [色彩管理与采样滤波 §1.5](../03-图形与GPU工程/色彩管理与采样滤波.md#15-hdr)。

### 5.4 AV1 / HEVC / VVC 选型

| 编码 | 专利/授权 | 硬件支持 | 适用 |
|---|---|---|---|
| H.264 | 授权体系成熟 | 全覆盖 | 兼容性兜底 |
| H.265/HEVC | 授权复杂 | 2015 年后设备广泛 | 4K/HDR 主流 |
| AV1 | 免版税（AOMedia） | 2019 年后逐步铺开 | 流媒体、低码率 |
| VVC/H.266 | 授权待明朗 | 新设备少量 | 前瞻 |

**AV1 硬件解码支持（数量级判断，必须实测）** ⚠️：

| 平台 | 大致情况 |
|---|---|
| Qualcomm 骁龙 8 Gen 1 及更新旗舰 | 普遍支持 AV1 硬解 |
| MediaTek 天玑 9000 及更新旗舰 | 多数支持 AV1 硬解 |
| Apple A17 Pro / M3 及更新 | 支持 AV1 硬解；更早机型多为软解 |
| NVIDIA RTX 30 系及更新 | 支持 AV1 硬解 |
| AMD RDNA2 及更新 | 支持 AV1 硬解 |
| Intel 11 代酷睿/Xe 及更新 | 多数支持 AV1 硬解 |

> 不要按"芯片型号"写死逻辑。运行时用 `MediaCodecList` 查询 `MediaCodecInfo` 的 MIME、`isHardwareAccelerated()`、`isSoftwareOnly()`，再决定是否启用 AV1。

### 5.5 DRM 与安全播放

| 层级 | 说明 |
|---|---|
| Widevine L1 | 解码与密钥在 TEE，支持 HD/HDR |
| Widevine L3 | 软件安全，通常限 480p/540p |
| PlayReady / FairPlay | 对应平台生态 |
| Secure decoder + secure surface | 内容不可截屏、不可读回 |

- 安全播放路径通常禁止 `glReadPixels`/截图，纹理化特效也会受限。
- 切档、切音轨不能改变 DRM 密钥体系，否则要重新授权。
- 车载多屏播放要确认每个显示路径都满足 DRM 要求。

## 6. 错误隐藏与恢复

### 6.1 网络层

| 问题 | 手段 |
|---|---|
| 分片 404/超时 | 重试 + 指数退避；切换 CDN/备用 URL |
| 丢包 | HTTP/2/3、QUIC、FEC（视协议） |
| 吞吐骤降 | ABR 降档；降低预取并发 |
| 直播断流 | 重新拉取 playlist；跳到 live edge |
| DRM 失败 | 重新获取 license；降级非 DRM 源（若业务允许） |

### 6.2 码流/解码层

| 问题 | 表现 | 处理 |
|---|---|---|
| NALU 缺失 | 花屏、绿块、灰帧 | 冻结上一帧；跳到下一个 I 帧 |
| 参考帧损坏 | 后续帧持续花 | 请求 IDR/关键帧；重建解码器 |
| 解码器错误 | `CodecException` | 区分可恢复/不可恢复；可恢复则 reset |
| 分辨率突变 | 解码器不接受 | 重建解码器并重新配置 |
| 音频丢包 | 爆音、断续 | PLC/静音渐变；重同步 |

FFmpeg 侧通常关注：

- `AVPacket.flags & AV_PKT_FLAG_CORRUPT`
- `avcodec_send_packet` / `avcodec_receive_frame` 的错误码
- `err_recognition` 与容错策略（不同版本参数名有差异）

Android 侧：

- `MediaCodec.OnErrorListener`
- `CodecException.isRecoverable()` / `isTransient()`
- `MediaCodec.reset()` 后重新 `configure/start`

### 6.3 恢复后的音画同步

1. 以音频主时钟为基准（或外部时钟）。
2. 视频落后太多：丢帧追赶；领先太多：等待或重复帧。
3. 恢复瞬间做音频淡入/淡出，避免爆音。
4. 直播长卡后直接跳到 live edge，而不是从旧位置慢慢追。

### 6.4 错误隐藏的体验原则

- **宁可冻结，不要黑屏**：冻结最后一帧比黑屏更可接受（倒车影像尤其如此）。
- **宁可降质，不要卡死**：降档、降分辨率、跳帧都可以接受。
- **恢复要无感**：静音渐变、画面淡入、时间轴对齐。
- **要有 watchdog**：解码/渲染线程长时间无输出时，主动重启管线。

## 7. 相机采集管线

### 7.1 Camera2 的五层对象

```
CameraManager
  └─ CameraDevice
      └─ CameraCaptureSession
          ├─ CaptureRequest（预览/拍照/分析）
          └─ Surface（Preview / ImageReader / MediaCodec / MediaRecorder）
```

| 对象 | 作用 |
|---|---|
| `CameraManager` | 枚举相机、查询 `CameraCharacteristics` |
| `CameraDevice` | 打开/关闭相机 |
| `CameraCaptureSession` | 提交请求、接收结果 |
| `CaptureRequest` | 指定目标 Surface 与参数（曝光/对焦/FPS） |
| `Surface` | 输出目的地：预览、分析、编码、拍照 |

### 7.2 三种输出路径

| 路径 | Surface 来源 | 数据形态 | 用途 |
|---|---|---|---|
| 预览 | `SurfaceView` / `TextureView` | PRIVATE（GPU 可采样） | 实时预览 |
| 分析 | `ImageReader` | YUV_420_888 / JPEG / RAW | 人脸、检测、美颜 |
| 录制 | `MediaCodec` input Surface | PRIVATE | 视频编码 |

### 7.3 零拷贝预览

```
Sensor → ISP → Gralloc Buffer
   → ImageReader/SurfaceTexture → OES 外部纹理
   → Shader 处理 → 合成上屏
```

关键点：

- 预览通常用 `SurfaceTexture` 绑定 `Surface`，直接生成 OES 外部纹理；需要拿到底层硬件缓冲区时，可用 `ImageReader` 的 `PRIVATE` 格式配合 `Image.getHardwareBuffer()`（API 28+），避免 CPU 读 YUV ⚠️。
- `SurfaceTexture` + `GL_TEXTURE_EXTERNAL_OES` 是相机预览进入 GL 的标准入口。
- API 26+ 可用 `AHardwareBuffer` + `EGLImage` 做更底层的共享。
- `ImageFormat.YUV_420_888` 的三个 plane 有各自 row/pixel stride，不能假设连续内存。
- `acquireLatestImage()` 会丢弃旧帧，适合实时预览；`acquireNextImage()` 适合逐帧处理；每张 `Image` 必须 `close()`，否则管线堵塞。

### 7.4 CameraX

| UseCase | 作用 |
|---|---|
| `Preview` | 预览 |
| `ImageAnalysis` | 逐帧分析（可设 `STRATEGY_KEEP_ONLY_LATEST`） |
| `ImageCapture` | 拍照 |
| `VideoCapture` | 录像 |

CameraX 解决生命周期、设备兼容与 UseCase 组合，适合业务快速落地；需要精细控制（多路流、手动曝光、RAW、低延迟）时仍要回到 Camera2。

### 7.5 时间戳与同步

- 相机帧时间戳来自 `SENSOR_TIMESTAMP`（纳秒），不是 `System.currentTimeMillis()`。
- 音视频同步要以相机时间戳或音频时钟为基准，不能各自用本地时间。
- 卷帘快门（rolling shutter）在快速运动/闪光灯下会形变；车载环视拼接要考虑。
- 多摄时间戳要硬件同步（部分平台支持），否则环视拼接会错位。

### 7.6 车载环视（AVM）

```
4 路鱼眼 → 硬件同步采集 → 去畸变（Brown-Conrady）→ 透视变换/鸟瞰
        → 拼接融合（接缝/亮度平衡）→ 3D 碗模型贴图 → GPU 渲染
```

- 标定参数（内参/外参/畸变系数）必须与安装位置一致。
- 拼接缝要做亮度/颜色均衡，否则四路画面"四块补丁"。
- 倒车/转向触发要低延迟，通常走独立高优先级管线。
- 功能安全要求：失效时冻结最后一帧或显示安全提示，不能黑屏。

## 8. 车载场景的特殊约束

| 约束 | 影响 | 应对 |
|---|---|---|
| 隧道/地库弱网 | 吞吐骤降、断流 | 大缓冲、保守 ABR、CDN 多路径 |
| 多屏独立播放 | 解码器实例有限 | 按屏分配码率/分辨率；后台降档 |
| 倒车影像优先级 | 必须 <2 s 显示 ❗ | 独立硬件路径、绕过普通 App 合成 |
| 功耗/发热 | 长时间播放降频 | 硬解、限制 4K、后台暂停 |
| 内容 DRM | 安全路径限制特效 | 安全解码 + 受保护 Surface |
| 功能安全 | 不能黑屏/卡死 | watchdog、冻结帧、降级提示 |
| 多摄像头 | 带宽/ISP 能力 | 硬件同步、按需分辨率 |

**倒车影像与普通播放的差异**：

- 普通播放可以缓冲、可以等首帧；倒车影像不能。
- 普通播放可以走 App 的 GL 特效链；倒车影像通常走 HWC/硬件直出。
- 普通播放失败可以重试；倒车影像失败必须保持最后一帧并报警。
- 法规时间要求（FMVSS 111 约 2 秒）以最新法规与车型要求为准 ❗。

## 9. 自测问答

**Q1：HLS 和 DASH 的核心区别？**
HLS 用 m3u8 + 分片，生态简单、Apple 友好；DASH 用 MPD XML，结构更工程化，支持多 Period、多语言、CENC 更完整。CMAF 让两者共享同一套 fMP4 分片。

**Q2：CMAF 解决了什么问题？**
统一 fMP4 与 CENC，使同一份分片同时服务 HLS 和 DASH，降低 CDN 存储与转封装成本，也是低延迟 chunked 传输的基础。

**Q3：ABR 为什么不能只看吞吐？**
吞吐估计噪声大，短分片容易误判；只看吞吐会在缓冲充足时频繁升降档。工程上用"吞吐 + 缓冲水位 + 滞回"的混合策略。

**Q4：首帧慢怎么排查？**
按 DNS/TLS → manifest → 首片 → demux → 解码器初始化 → 首帧解码 → 纹理上传 → vsync 分段打点；先定位是网络、解码还是渲染。

**Q5：为什么 10bit 能减轻 banding？**
量化台阶更细，暗部渐变可用码值更多；配合 dither 可进一步打散残余台阶。但链路中任一环掉到 8bit 都会前功尽弃。

**Q6：P010 和 NV12 的区别？**
都是 4:2:0；P010 每个分量存在 16bit 容器里、有效 10bit（低 6 位补零），NV12 是 8bit。把 P010 当 NV12 上传会发绿/发灰。

**Q7：HDR10 和 HLG 的区别？**
HDR10 用 PQ 绝对亮度 + 静态元数据；HLG 用相对亮度、向后兼容 SDR，适合广播。两者都需要 BT.2020 与 10bit 才能发挥。

**Q8：怎么判断设备是否支持 AV1 硬解？**
运行时查 `MediaCodecList`，看 `video/av01` 的 `MediaCodecInfo` 是否 `isHardwareAccelerated()`；不要按芯片型号写死。

**Q9：丢包/坏帧怎么恢复？**
网络层重试/降档/切 CDN；码流层冻结上一帧、跳到下一个 I 帧、必要时重建解码器；恢复后按主时钟重新对齐音画。

**Q10：相机预览怎么做到零拷贝？**
`ImageReader`/`SurfaceTexture` 直接接收 ISP 输出的 Gralloc Buffer，绑定为 OES 外部纹理供 GPU 采样，避免 CPU 读 YUV 再上传。

**Q11：倒车影像为什么不能复用普通播放管线？**
普通管线有缓冲、特效链、App 合成，延迟不可控；倒车要求秒级内显示、失效不黑屏，通常走独立硬件直出与高优先级合成。

**Q12：直播卡顿后为什么要跳 live edge？**
长时间卡顿后旧缓冲已过期，继续从旧位置播放会越落越远；跳到 live edge 并重新建立缓冲，体验更接近"直播"。

## 10. 一页检查清单

**流媒体接入**

- [ ] manifest 与分片支持 HTTPS、Range、CDN 多路径
- [ ] 分片边界对齐关键帧，支持 ABR 切档
- [ ] 有启动缓冲与稳态缓冲两套策略
- [ ] TTFF、卡顿比、平均码率、切换次数有打点
- [ ] 弱网/断流有重试、降档、跳 live edge 策略

**HDR/10bit**

- [ ] 容器与码流元数据完整传递（primaries/transfer/matrix/range）
- [ ] 解码器输出格式与纹理格式匹配（P010 → R16/RG16）
- [ ] 显示能力查询后再决定 tone mapping
- [ ] 全链路没有中途掉到 8bit（除最终输出）
- [ ] 截图/录屏有 HDR→SDR 转换

**相机/车载**

- [ ] 预览走 OES/PRIVATE，避免 CPU 读 YUV
- [ ] `Image` 及时 `close()`，分析策略为 keep latest
- [ ] 使用 `SENSOR_TIMESTAMP` 做同步
- [ ] 倒车/环视有独立优先级与失效冻结策略
- [ ] 多摄有时间同步与标定参数校验

---

> **一句话总结**：文件播放拼的是解码与渲染；流媒体拼的是"在带宽波动下稳定地把首帧送上来"；实时采集拼的是"不经过 CPU 把 sensor 数据送进 GPU"。三者共用同一条解码/渲染主干，但失败模式完全不同。
