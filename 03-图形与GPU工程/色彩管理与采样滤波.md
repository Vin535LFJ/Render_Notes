## 1. 色彩空间与传输函数

### 1.1 三个容易混淆的概念

| 概念 | 回答的问题 | 例子 |
|---|---|---|
| **色彩空间（primaries）** | 红绿蓝三个基色在色度图上的位置 | Rec.709、Rec.2020、Display P3 |
| **传输函数（transfer）** | 编码值 ↔ 线性光强的关系 | sRGB、gamma 2.2、PQ、HLG |
| **矩阵系数（matrix）** | YUV 与 RGB 之间怎么换算 | BT.601、BT.709、BT.2020 |

视频元数据里这三者是**独立字段**：`colour_primaries`、`transfer_characteristics`、`matrix_coeffs`。只改矩阵不改 primaries，颜色仍会偏。

### 1.2 sRGB 传输函数

sRGB 不是简单的 `pow(x, 2.2)`，而是分段函数：

$$
C_{linear} =
\begin{cases}
C_{srgb} / 12.92, & C_{srgb} \le 0.04045 \\
\left(\frac{C_{srgb} + 0.055}{1.055}\right)^{2.4}, & C_{srgb} > 0.04045
\end{cases}
$$

- 暗部是线性段，避免 `pow` 在 0 附近的无穷斜率。
- 近似用 2.2 在大多数场景够用，但**精确匹配**要用上面的公式。
- Alpha 通道**永远不参与**传输函数变换。

### 1.3 线性工作流

```
sRGB 纹理 --(sRGB 解码)--> 线性 --(光照/混合)--> tone mapping --(sRGB 编码)--> 显示
```

**为什么必须线性**：

- 光照的加乘、Alpha 混合、模糊，物理上都对应线性光强。
- 在 gamma 空间做混合，半透明边缘会偏暗/偏亮；模糊会发灰。
- 在 gamma 空间做光照，暗部对比过强，高光容易爆。

**工程做法**：

| 环节 | 做法 |
|---|---|
| 颜色纹理 | 上传为 `GL_SRGB8_ALPHA8` / `VK_FORMAT_R8G8B8A8_SRGB`，硬件自动解码 |
| 数据纹理（法线/粗糙度/遮罩） | 保持线性格式，**不要** sRGB |
| 帧缓冲 | 用 sRGB 格式让硬件编码；或手动 `pow(1/2.2)` |
| 混合 | 在线性空间做（sRGB 帧缓冲的混合由硬件在线性空间完成） |
| UI | 通常在 sRGB 空间合成，注意与 3D 的边界 |

> 常见错误：把法线贴图设成 sRGB，导致法线方向被 gamma 扭曲，光照"发脏"。

### 1.4 YUV 与 range

| 项目 | Limited（视频） | Full（JPEG/屏幕） |
|---|---|---|
| Y | 16–235 | 0–255 |
| U/V | 16–240 | 0–255 |
| 转换前 | 先减偏移 `(16,128,128)` | 直接转换 |

BT.601/709/2020 的矩阵不同，必须由元数据选择。完整矩阵见 [图形与GPU工程 §2.2](图形与GPU工程.md)。

### 1.5 HDR

| 标准 | 传输函数 | 特点 |
|---|---|---|
| **PQ（ST2084）** | 绝对亮度映射（0–10000 nit） | HDR10 / Dolby Vision 基础 |
| **HLG** | 相对亮度，兼容 SDR | 广播 |
| **SDR** | sRGB / gamma 2.2 | 主流车载屏 |

**渲染侧要点**：

- HDR 渲染目标通常是 `R16G16B16A16_FLOAT`，在线性空间做光照。
- tone mapping 把 HDR 映射到显示能力：Reinhard、ACES、Filmic、AgX。
- 输出到 PQ 屏需要按 ST2084 编码，并考虑面板峰值亮度与 surroundings。
- 车载屏幕亮度范围有限，HDR 主要用于高端座舱；普通屏重点是**不过曝、不偏色、暗部可辨**。

> 播放链路的 10bit/P010、VUI/Dataspace 元数据与 tone mapping 插入位置见 [流媒体、HDR 与实时采集 §5](../02-解码与播放链路/流媒体与实时采集.md#5-10bithdr-与-av1)。

### 1.6 色域映射

- Rec.709 → Rec.2020 不是简单矩阵，需要 gamut mapping（否则高饱和色会越界）。
- Display P3 比 sRGB 宽约 25%，直接把 sRGB 内容标成 P3 会"变艳"。
- 车载多屏可能色域不同，需要统一到工作空间再输出。

## 2. 采样与滤波

### 2.1 纹理过滤模式

| 模式 | 行为 | 用途 |
|---|---|---|
| `NEAREST` | 取最近像素 | 像素风、数据纹理、精确读取 |
| `LINEAR` | 双线性插值（2×2） | 通用放大/缩小 |
| `NEAREST_MIPMAP_NEAREST` | 选一层 mip，再最近采样 | 低成本 |
| `LINEAR_MIPMAP_NEAREST` | 选一层 mip，双线性 | 常用 |
| `LINEAR_MIPMAP_LINEAR` | 两层 mip 三线性 | 质量优先 |
| **各向异性** | 按视角方向多采样 | 地面/路面/远处纹理 |

### 2.2 放大与缩小

- **放大（magnification）**：纹理分辨率低于屏幕，双线性会糊；高质量可用 bicubic/Lanczos（成本高）。
- **缩小（minification）**：纹理分辨率高于屏幕，必须用 mipmap，否则出现**摩尔纹/闪烁**。
- mipmap 的 LOD 由屏幕空间导数自动计算：`lod = log2(max(|dFdx(uv)|, |dFdy(uv)|) * texSize)`。

### 2.3 Mipmap 的坑

| 问题 | 原因 | 解决 |
|---|---|---|
| 图集串色 | mip 层级把相邻图块混合 | padding / 手动生成 mip / 关闭 UI mipmap |
| 文字发糊 | 过度使用 mip | UI 关闭 mipmap 或提高分辨率 |
| 接缝 | UV 在边界 | `CLAMP_TO_EDGE` + 半像素内缩 |
| 闪烁 | 未生成 mip 或 LOD bias 不当 | 生成完整 mip 链，调 `GL_TEXTURE_LOD_BIAS` |

### 2.4 各向异性过滤

- 当表面与视线夹角很小（地面、路面、长走廊），一个像素覆盖的纹理区域是长条形，各向同性 mip 会过度模糊。
- 各向异性过滤沿长轴多次采样（2×/4×/8×/16×），显著改善远处地面清晰度。
- 成本随采样数增长；移动端常用 2×/4×，并受 `GL_MAX_TEXTURE_MAX_ANISOTROPY_EXT` 限制。

### 2.5 Wrap 模式

| 模式 | 行为 | 用途 |
|---|---|---|
| `REPEAT` | 平铺 | 地面、墙面 |
| `CLAMP_TO_EDGE` | 边缘拉伸 | 图集、FBO 纹理、UI |
| `MIRRORED_REPEAT` | 镜像平铺 | 特殊图案 |
| `CLAMP_TO_BORDER` | 边界色（桌面 GL） | 阴影/后处理 |

**FBO 纹理默认是 `REPEAT`**，不做后处理时容易在边缘采到对侧像素，务必设成 `CLAMP_TO_EDGE`。

### 2.6 采样质量与性能

- 每次 `texture()` 都是一次带宽访问；三线性 + 各向异性会成倍增加。
- 移动端 TMU 数量有限，采样密集的 shader 容易成为瓶颈。
- 能用顶点插值解决的，不要放片元采样；能合并的纹理通道（打包 R/G/B/A）要合并。
- `textureLod` 在片元中可显式指定 LOD，避免导数计算；但会失去自动适配。

## 3. 显示与量化

### 3.1 色深与 banding

- 8-bit 每通道只有 256 级，暗部渐变容易出现**色带（banding）**。
- 解决：抖动（dithering）、更高色深（10-bit）、加噪声。
- 10-bit 输出需要 `GL_RGB10_A2` / `VK_FORMAT_A2B10G10R10` 与显示链路支持。

### 3.2 抖动（Dithering）

```glsl
// 简单有序抖动（4x4 Bayer）
float bayer4(vec2 p) {
    int x = int(mod(p.x, 4.0));
    int y = int(mod(p.y, 4.0));
    const float m[16] = float[](
         0.0,  8.0,  2.0, 10.0,
        12.0,  4.0, 14.0,  6.0,
         3.0, 11.0,  1.0,  9.0,
        15.0,  7.0, 13.0,  5.0);
    return m[y * 4 + x] / 16.0;
}
// color += (bayer4(gl_FragCoord.xy) - 0.5) / 255.0;
```

- 抖动把量化误差打散到空间上，人眼更不易察觉色带。
- 视频/UI 输出前加轻微抖动可显著改善暗部。

### 3.3 色彩管理链路检查清单

- [ ] 颜色纹理是否 sRGB 格式？
- [ ] 法线/粗糙度/AO 是否保持线性？
- [ ] 光照与混合是否在线性空间？
- [ ] tone mapping 是否在 bloom 之后？
- [ ] 输出是否做了 sRGB/PQ 编码？
- [ ] YUV 的矩阵与 range 是否按元数据？
- [ ] FBO 纹理是否 `CLAMP_TO_EDGE`？
- [ ] UI 与 3D 的合成空间是否一致？

## 4. 十个高频问答

### Q1：为什么画面整体发灰？

> 最常见是"双重 gamma"或"缺失 gamma"：纹理已经是 sRGB 解码后的线性值，又手动 `pow(1/2.2)`；或者在线性空间渲染后直接输出，没有编码。检查纹理格式、帧缓冲格式、后处理链里是否有重复转换。

### Q2：为什么半透明边缘发黑？

> 直通 Alpha 在双线性插值时，透明像素的 RGB（通常是黑）会污染边缘。解决：预乘 Alpha，并使用 `GL_ONE, GL_ONE_MINUS_SRC_ALPHA`。

### Q3：为什么远处纹理闪烁？

> 没有 mipmap 或 mipmap 不完整，缩小采样时发生 aliasing。生成完整 mip 链，使用三线性/各向异性过滤，必要时调 LOD bias。

### Q4：为什么法线贴图会让光照"发脏"？

> 法线贴图被当作 sRGB 解码，或压缩格式（如 ETC1S）损失了方向精度，或 TBN 未正交化。法线必须是线性数据，压缩要用高质量格式（UASTC/ASTC）。

### Q5：sRGB 帧缓冲的混合是在线性空间吗？

> 是。启用 sRGB 帧缓冲后，硬件在写入时把线性颜色编码为 sRGB，读取时解码，混合在线性空间完成。这也是为什么"直接用 sRGB 纹理 + sRGB 帧缓冲"通常能得到正确结果。

### Q6：YUV 的 limited/full range 搞错会怎样？

> limited 当 full 用会发灰、对比度低；full 当 limited 用会发白、暗部被压死。必须按容器/码流元数据选择，不能凭经验硬编码。

### Q7：各向异性过滤为什么能改善地面？

> 斜视时像素覆盖的纹理区域是长条形，各向同性 mip 只能选一个整体模糊层级；各向异性沿长轴多次采样，保留方向细节。代价是采样数增加。

### Q8：10-bit 显示能解决 banding 吗？

> 能显著改善，但前提是全链路 10-bit（纹理、FBO、合成、面板）。如果中间仍是 8-bit，提升有限。抖动在 8-bit 链路上仍是有效手段。

### Q9：HDR 渲染一定要用浮点 RT 吗？

> 通常需要，因为高光可能远大于 1.0。也可以用 `R11G11B10F` 等等效格式节省带宽。最终输出前必须 tone mapping 到显示范围。

### Q10：纹理打包（channel packing）有什么注意点？

> 把粗糙度/AO/金属度塞进不同通道，减少采样次数与带宽；但这些通道必须都是线性数据，不能与 sRGB 混用；压缩格式的通道精度可能不同，关键通道放在高精度位置。

## 5. 一页速记

```
三件事：primaries / transfer / matrix，缺一不可
线性工作流：解码 → 光照混合 → tone map → 编码
Alpha 不参与 gamma；法线不 sRGB
缩小必 mipmap，斜视要各向异性
FBO 纹理 CLAMP_TO_EDGE
8-bit 有色带 → 抖动 / 10-bit
```
