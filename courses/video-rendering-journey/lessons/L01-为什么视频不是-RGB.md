# 为什么视频不是 RGB

> **本章回答**：视频文件里的一帧，为什么不直接存成屏幕能显示的 RGB，而要先绕一道 YUV？
> **写作纪律**：正文用自己的语言展开推导，权威定义与完整细节链接主文档锚点，不整篇复制；陌生术语首次出现给出一句话解释。
> **路线位置**：pilot 路线第 1 课（L01 → L02 → L06 → L11 → L13），建议 45 分钟，含动手实验。

## 1. 从一个问题开始

先算一笔账。一张 1920×1080 的 RGBA8888 图片——每个像素存红、绿、蓝、透明度四个通道，各占 1 字节——需要：

$$
1920 \times 1080 \times 4 = 8{,}294{,}400 \ \text{字节} \approx 8.29 \ \text{MB}
$$

一段 90 秒、30fps 的视频有 2700 帧。如果每帧都这样存：

$$
2700 \times 8.29 \ \text{MB} \approx 22.4 \ \text{GB}
$$

而同样 90 秒、码率 10 Mbps 的 H.264 视频只有约 **112.5 MB**（10 Mbps = 每秒 1.25 MB）。两者相差约 **200 倍**。一部高清电影几 GB 就能装下，靠的就是这 200 倍。

这 200 倍是两刀砍出来的：

- **第一刀：像素格式**。不存 RGB，改存 YUV——每像素从 4 字节降到 1.5 字节，省掉 62.5%（约 2.67 倍）。
- **第二刀：压缩编码**。H.264 等编码器利用帧内/帧间冗余再压约 75 倍。

这一章只讲第一刀。它要回答三个问题：**为什么砍颜色人眼几乎看不出来？砍完的数据在内存里长什么样？为什么读这块内存时还有一个叫 stride 的陷阱？**

> 数字口径：本章 MB 为十进制（10⁶ 字节）、MiB 为二进制（2²⁰ 字节），不混读——这是[主文档 §1](../../../01-基础理论/音视频基础理论.md#1-媒体处理三层数据模型)明确要求的纪律。8.29 MB 即 7.91 MiB。

## 2. 学习前提

- 知道一帧图像由像素组成、分辨率是"宽×高"；会做乘法。不需要任何编解码经验。
- 建议先看过 [L00 知识地图](../../../00-导航与索引/知识架构总览.md#1-知识地图)，知道本课属于 L1 基础理论层。
- 两个首次出现的术语，先给一句话解释：
  - **RGB**：用红（R）绿（G）蓝（B）三个分量表示一个像素的颜色；RGBA8888 是再加一个透明度通道 A、每通道 8 位的存储格式。
  - **色彩空间**：一套"用什么分量、按什么规则表示颜色"的约定。RGB 是一种，YUV 是另一种。完整定义见[术语表](../../../00-导航与索引/验真队列与术语表.md)与[主文档 §2](../../../01-基础理论/音视频基础理论.md#2-像素格式与色彩空间)。

## 3. 直观认识

把一张彩色照片拆成两部分：一张**黑白照片**，和两张**涂色底图**。

- 黑白照片记录每个像素的明暗——这是**亮度 Y**。
- 涂色底图记录"这块区域偏什么颜色"——这是**色度 U/V**。

关键观察：黑白照片必须清晰，涂色底图可以模糊。你可以现在就验证——眯起眼睛看一张色彩丰富的图：轮廓和明暗细节还在，颜色却糊成一片。这不是错觉，是眼睛的硬件特性：视网膜里对明暗敏感的杆状细胞远多于对色彩敏感的锥状细胞，**人眼分辨颜色细节的能力远弱于分辨明暗**（断言 `V13`，依据见[主文档 §2.1](../../../01-基础理论/音视频基础理论.md#21-yuv-色彩空间与采样格式)）。

既然颜色细节看不清，那就少存颜色：**每 2×2 个像素共用一组 U/V**。这就是 **YUV 4:2:0**——色度采样只有亮度的四分之一。

> **类比的边界**：涂色底图只是直觉模型。真实的 U/V 不是"涂色指令"，而是每个 2×2 块一对具体的色度数值（蓝色差/红色差），还原时要和 Y 一起做矩阵运算（那是 L06 纹理桥的事）。类比帮你记住"明暗精细、颜色粗糙"，别把它当成存储格式本身。

## 4. 一步一步理解原理

### 4.1 为什么把亮度单独拿出来

上一节的生理事实给出了工程许可：色度可以降采样而观感损失很小。于是 YUV 把亮度 Y 独立成通道，色度 U/V 单独存放、单独降采样。

历史上还有一层常被提及的动机：彩色电视广播要让黑白电视机也能收看——黑白电视只读亮度通道即可。YUV 的分离设计恰好兼容了这个需求。（这是历史背景叙述，帮助学生理解"为什么是 YUV 而不是别的"；它不是本课的注册断言，候选登记见诊断文档。）

注意因果顺序：**先有"人眼对色度迟钝"这个事实，才有"少存色度"这个设计**。省空间是结果，不是出发点。

### 4.2 4:2:0 到底在说什么

"4:2:0" 三个数字描述亮度与两个色度分量的采样比例：以 4 个亮度采样为基准，第一行色度采 2 个，第二行色度采 0 个（沿用上一行）——合起来就是 **2×2 像素块共享 1 个 U 和 1 个 V**：

```
像素网格（2×2）          采样结果
┌─────┬─────┐
│ Y00 │ Y01 │            Y：4 个，逐像素独立
├─────┼─────┤            U：1 个，整块共享
│ Y10 │ Y11 │            V：1 个，整块共享
└─────┴─────┘
```

对照另外两种采样，建立"省了多少"的数感（每 2×2 块）：

| 采样格式 | 色度规则 | 块内字节数 | 每像素字节 |
|---|---|---|---|
| 4:4:4 | 每像素独立 U/V | 4Y+4U+4V = 12 | 3 |
| **4:2:0** | 2×2 共享一组 U/V | 4Y+1U+1V = **6** | **1.5** |
| RGBA8888 | 每像素 4 通道 | 16 | 4 |

所以"4:2:0 省一半"是相对 **4:4:4** 说的（12→6）；"省 62.5%"是相对 **RGBA8888** 说的（16→6）。两个基准，两个数字，别混（断言 `V12` 的成立条件就是 4:2:0 采样）。

### 4.3 内存里长什么样：I420、NV12、NV21

采样规则定了"存多少"，**排布规则**定了"怎么放"。4:2:0 有两大排布家族：

- **Planar（平面）**：Y、U、V 各占一个独立连续平面。代表 **I420**（顺序 Y→U→V，FFmpeg 软解默认输出）；YV12 只是把 U/V 平面顺序对调。
- **Semi-Planar（半平面）**：Y 一个平面，U/V **交错**放在第二个平面。代表 **NV12** 与 **NV21**。

NV12 的内存布局（W×H 图像）：

```
偏移 0 ┌──────────────────────────────┐
       │ Y 平面：W × H 字节            │  每像素 1 字节亮度
       ├──────────────────────────────┤
       │ UV 平面：W × H / 2 字节       │  U V U V U V … 交错
       └──────────────────────────────┘
```

**NV12 与 NV21 的唯一差别是交错顺序**：NV12 是 U-V-U-V…，NV21 是 V-U-V-U…（断言 `V02`）。一个 swap 而已，为什么值得单独记？因为平台约定不同：iOS 视频链路默认 NV12，Android **相机**默认输出 NV21，FFmpeg 软解默认 I420（平台差异表见[主文档 §2.1](../../../01-基础理论/音视频基础理论.md#21-yuv-色彩空间与采样格式)）。跨平台搬代码时，把 NV21 当 NV12 读，U/V 整体颠倒，画面立刻偏色——肤色发蓝紫、天空发黄，这是最常见的花屏原因之一。

### 4.4 Stride：为什么行宽不等于图像宽

现在你有一块 YUV 内存，准备按行读出来。陷阱来了：**每行的物理字节数（stride，又称 pitch）通常大于"图像宽度×每像素字节数"**。

为什么？因为硬件不按"人类的宽度"读内存。解码器、GPU、DSP 通过 DMA（直接内存访问，一种不经过 CPU 逐字节搬运的传输机制——DRAM/DMA/PCIe 三个概念的区分见[概念引入说明 §1](../../../00-导航与索引/概念引入说明.md#1-数据通路dram-dma-pcie-各是什么)，断言 `E01`）或缓存行批量加载数据，要求行宽对齐到硬件边界（典型 64/128 字节，**因芯片平台而异**）。宽度不够就补 padding：

$$
\text{Stride} = \left\lceil \frac{W}{\text{对齐基数}} \right\rceil \times \text{对齐基数}
$$

算例：128 字节对齐的平台上，逻辑宽度 1080 像素（Y 平面每像素 1 字节）：

$$
\text{Stride} = \left\lceil \frac{1080}{128} \right\rceil \times 128 = 9 \times 128 = 1152 \ \text{字节}
$$

每行末尾多出 **72 字节**的无意义填充。公式与算例的权威版本见[主文档 §Stride 计算公式](../../../01-基础理论/音视频基础理论.md#stride-计算公式)（断言 `V14`）。

**忽略 stride 会发生什么？推一遍就懂。** 假设你按逻辑宽度 1080 逐行读取：

```
物理内存（stride = 1152）：
行0: [1080 有效字节][72 padding]
行1: [1080 有效字节][72 padding]
行2: [1080 有效字节][72 padding]

按宽度 1080 计算行起点：
行0 起点 = 0      ✓ 正确
行1 起点 = 1080   ✗ 应为 1152，偏了 72 字节
行2 起点 = 2160   ✗ 应为 2304，偏了 144 字节
行n 起点 = n×1080 ✗ 累积偏差 n×72 字节
```

每一行都比上一行多错 72 字节，误差**逐行累积**——画面整体被"剪切"成斜纹。这就是"斜向倾斜"故障的完整机制，不是玄学。

还有两个连带现象，都能从 padding 推出来：

- **绿色线条**：padding 字节通常填 0。把 0 当像素读，得到 YUV=(0,0,0)。用实验里的 full-range BT.601 近似公式算一下：R = 0 + 1.402×(0−128) ≈ −179 → 截断为 0；G = 0 − 0.344×(0−128) − 0.714×(0−128) ≈ 135；B = 0 + 1.772×(0−128) ≈ −227 → 截断为 0。结果是 **(0, 135, 0)——纯绿**。所以错位读到的 padding 显示为绿线。
- **全局绿屏**：如果色度平面整体寻址错位，U/V 全错，整帧偏绿。

故障现象与根因的完整对照表见[主文档 §忽略 Stride 的后果](../../../01-基础理论/音视频基础理论.md#忽略-stride-的后果)。正确做法是上传纹理时告诉驱动真实行宽（以 GLES3 的 Y 平面为例，每像素 1 字节，行宽字节数恰等于行宽像素数）：

```c
glPixelStorei(GL_UNPACK_ROW_LENGTH, stride);  // 按物理行宽跳读，跳过 padding
glTexImage2D(GL_TEXTURE_2D, 0, GL_R8, width, height, 0,
             GL_RED, GL_UNSIGNED_BYTE, yPlane);
glPixelStorei(GL_UNPACK_ROW_LENGTH, 0);       // 恢复默认，避免影响后续上传
```

注意：`GL_UNPACK_ROW_LENGTH` 的单位是**像素**，多字节格式要按每像素字节数换算；UV 平面有自己的 stride，行高也可能被对齐（16/32 行），思路相同。对齐基数与行高规则因平台而异，具体参数查 SoC 手册——这是断言 `V14` 的成立条件。

## 5. 数学原理 / 数据形态

把 §4.2 的块级账放大到整帧，得到本章的核心公式（断言 `V12`，推导见[主文档 §内存计算公式](../../../01-基础理论/音视频基础理论.md#内存计算公式)）：

$$
\text{Memory}_{\text{YUV420}} = W \times H \times \left(1 + \tfrac{1}{4} + \tfrac{1}{4}\right) = W \times H \times 1.5 \ \text{字节}
$$

$$
\text{Memory}_{\text{RGBA8888}} = W \times H \times 4 \ \text{字节}
\qquad
\frac{1.5}{4} = 0.375 \ \Rightarrow\ \text{节省 } 62.5\%
$$

1080p 实例：YUV420 单帧 3,110,400 字节（≈3.11 MB / 2.97 MiB），RGBA8888 单帧 8,294,400 字节（≈8.29 MB / 7.91 MiB）。

回到开篇的账：第一刀把 22.4 GB 砍到约 8.4 GB（2700 × 3.11 MB），剩下的约 75 倍由压缩编码完成——**YUV 是像素表示，不是压缩编码**。这是原始层（Raw Layer）的体积，不是文件体积；三层数据模型（压缩层/原始层/显示层）见[主文档 §1](../../../01-基础理论/音视频基础理论.md#1-媒体处理三层数据模型)。

## 6. 工程应用与常见错误

**一个典型的排查现场**（由[主文档故障表](../../../01-基础理论/音视频基础理论.md#忽略-stride-的后果)重组的教学案例）：某设备上预览画面出现斜向条纹，边缘还有绿线。按本章机制倒推：斜纹 = 行起点逐行累积偏移 → 查 stride；绿线 = padding 的 0 被当像素 → 佐证 stride 错位。读解码器输出的实际 stride（而不是假设等于宽度），按 §4.4 的方式上传，故障消失。如果画面是**整体偏色**而不是斜纹，方向就不同了：先查 NV12/NV21 是否搞反（§4.3），再查 YUV→RGB 矩阵是否匹配色彩空间（L03/L06 的范围）。

常见误区：

- **"YUV 是一种压缩编码。"** 错。YUV 是像素表示（第一刀），压缩由 H.264 等编码器完成（第二刀）。
- **"照图像宽度读每行就行。"** 错。忽略 stride 会逐行错位、斜纹花屏，padding 还会带来绿线（§4.4 推导）。
- **"NV12 和 NV21 差不多。"** 交错顺序差一个 swap，颜色整体颠倒；跨平台（尤其 Android 相机 NV21 → iOS/硬解 NV12 链路）必须显式确认。
- **"YUV420 省 62.5% 是相对任何格式。"** 错。62.5% 的基准是 RGBA8888；相对 4:4:4 是省 50%。说数字必须带基准。

## 7. 动手实验

打开 [YUV↔RGB 实验](#/lab/yuv-to-rgb)（定义在 `tools/labs.json`，离线可运行）。带着四个任务做，每个任务对应本章一个机制：

1. **把 U、V 拉到 128 之外**，观察色度如何给 4 个像素**同时**染色——验证 §4.2"整块共享一组 U/V"。
2. **切换 4:4:4 → 4:2:0**，看字节布局从 12 B 收缩到 6 B——验证 §5 的块级账。
3. **给 4 个像素不同的 Y**，确认亮度始终逐像素独立——验证"明暗精细、颜色粗糙"。
4. **把 Y 拉到 235 以上 / 16 以下**，观察 limited range 造成的裁剪——这是本章没展开的数值范围约定，L03 会专门讲。

做完用实验内置的三道 selfTest 自查（6 字节怎么来的 / NV12 与 NV21 差异 / stride 忽略后果）。注意实验边界：它用 **full-range BT.601 近似公式**做教学演示；真实 Android 硬解链路多为 limited range，且 BT.601/709/2020 系数不同——矩阵用错会整体偏色（实验 note 原文如此，这正是 §6 排查现场的第二条线索）。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**人眼对亮度敏感、对色度迟钝（V13）→ 亮度/色度分离，色度可降采样 → 4:2:0 每 2×2 块共享一组 U/V → 每像素 1.5 字节，相对 RGBA8888 省 62.5%（V12）→ 排布分 planar/semi-planar，NV12/NV21 只差交错顺序（V02）→ 硬件对齐产生 stride（V14）→ 按 stride 读，否则斜纹/绿线/绿屏。**

再自问三个"为什么"：为什么省空间的第一刀砍的是颜色而不是明暗？为什么 NV12/NV21 一个 swap 值得单独记？为什么 padding 的 0 显示出来是绿色？
